The host application manages the user session, model context, and policy. Each MCP client maintains a protocol connection to a server. A server exposes capabilities over an agreed transport. Initialization negotiates protocol version and capabilities; discovery describes what exists, not what every user is authorized to use. A tool list is not a permission grant.

Tools are callable operations, resources are addressable contextual data, and prompts are reusable interaction templates. The host decides what to expose to the model; servers still validate identity and access for each request. Keep transport/protocol errors distinct from tool execution errors. Pin this course's implementation contract to the 2025-06-18 specification and record the actual SDK version; reconcile differences explicitly rather than mixing tutorial versions.

MCP host, clients, and servers

Protocol responsibilities

host

Client
The MCP client maintains a protocol connection to a server on behalf of its host application.
Server
The MCP server exposes capabilities and enforces its own resource and operation boundaries.
Tools
MCP tools describe callable operations whose proposed arguments still require policy checks.
Resources
MCP resources expose addressable content that the host may supply as context.
Prompts
MCP prompts provide reusable message templates rather than authority to execute actions.
Stdio
Use standard input and output for a local MCP process while keeping logs off the protocol stream.
Streamable HTTP
Use HTTP-based MCP communication with transport, authentication and connection behavior handled explicitly.
Schemas
Declare the structure of inputs and outputs so callers can validate protocol and tool data.
Authorization
Check the authenticated caller's permitted operation and data scope at the execution boundary.
Capability discovery
Negotiate protocol capabilities and inspect advertised tools or resources before using them.
Error handling
Distinguish protocol errors, tool failures and unknown effects so callers choose a safe next step.

Work through an example

One host connects client A to a document server and client B to a metrics server. The model proposes fetch_section. The host gates the call, client A carries the protocol request, and the document server independently enforces source scope. The metrics server never receives unrelated documents.

Separate tool access from protocol discovery

Use the tools discussion to distinguish exposing an operation from authorizing a caller. Apply that distinction to the MCP host and server.

Exercise

Apply the explanation

A discovered MCP tool advertises delete_document. Does its presence allow the model to execute it for the current user?

Read the explanation

No. Discovery announces a capability. Host policy can withhold it, and server-side authorization must reject unauthorized requests regardless of what the model or client proposes.

Cheat sheet

MCP host, client, and server boundaries

Definition

An MCP host uses clients to connect to servers that expose tools, resources and prompts.

Intuition

The protocol describes capabilities; the application still owns authorization.

Pattern

Implement initialize, capability discovery, one search tool, one resource, and one prompt using pinned dependencies.

Common mistake

A discovered tool is not automatically safe or permitted for every user.

Production notes

Pin compatible SDK versions, validate schemas and enforce per-request scope.
