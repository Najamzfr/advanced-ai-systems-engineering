A transactional outbox commits application state and an intent-to-send record in the same database transaction. A dispatcher retries the outbox record using a stable effect key. The external sink must deduplicate or expose status for reconciliation. This closes common dual-write gaps but does not magically make every external service exactly once.

If an effect succeeds and the worker crashes before recording success, the next attempt first reconciles the same key. Compensation is a new business action that repairs or offsets a prior effect; it is not time travel and may also fail. Bind human approval to the exact action and recheck it at dispatch. Keep attempt IDs distinct from the logical effect ID so repeated delivery remains auditable.

Exercise

Apply the explanation

The sink has neither idempotency keys nor a status query. Can the outbox alone guarantee no duplicate dispatch?

Read the explanation

No. A crash-after-effect remains ambiguous. Use a deduplicating adapter/sink where possible or surface UNKNOWN for manual reconciliation. Do not claim exactly-once behavior from local transactions alone.

Cheat sheet

Outbox, idempotency, and compensation

Definition

A durable workflow records progress so interrupted work can resume after a failure.

Intuition

Recovery must reconcile external effects, not only restart computation.

Formula

effect_key=hash⁡(workflow_id,logical_action_id)\mathrm{effect\_key}=\operatorname{hash}(\mathrm{workflow\_id},\mathrm{logical\_action\_id})

Derive identity from the logical action, not from a retry attempt. Store the action result and reconcile unknown outcomes.

Common mistake

Retrying a timed-out write can duplicate an effect that already happened.

Production notes

Use checkpoints, stable idempotency keys, bounded retries and compensation.
