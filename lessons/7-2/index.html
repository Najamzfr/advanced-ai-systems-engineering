Cron schedules, webhooks, and event streams are different ways to trigger work. Normalize them into a stable event identity and a versioned payload. A durable workflow persists state so a worker can restart after a process failure or long approval wait. A DAG describes dependencies; the runtime records what actually completed.

Acknowledge an event only after its accepted state is durable. Use bounded retries with backoff for transient failures, separate nonretryable validation errors, and move poison work to a dead-letter queue with a reason and safe replay procedure. Checkpoint input/output versions, not only a step number. A checkpoint saying "done" without the corresponding artifact cannot safely resume.

Durable workflow

effect_key=hash⁡(workflow_id,logical_action_id)\mathrm{effect\_key}=\operatorname{hash}(\mathrm{workflow\_id},\mathrm{logical\_action\_id})

Derive identity from the logical action, not from a retry attempt. Store the action result and reconcile unknown outcomes.

Recovery requirements

Study:

Cron
Start work on a schedule while handling overlapping runs and missed execution windows.
Webhooks
Receive externally triggered events and validate their origin before enqueueing work.
Queues
Buffer pending work with bounded capacity, deadlines and explicit delivery semantics.
Events
Represent something that happened with a stable identity and enough data to process it reproducibly.
DAGs
Represent acyclic task dependencies so runnable work and blocked work can be distinguished.
Durable execution
Persist progress so a restarted worker can resume without blindly repeating completed effects.
Checkpoints
Save task state at defined boundaries so restart behavior is explicit and testable.
Retries
Repeat transiently failed work within limits after checking whether the earlier attempt may have succeeded.
Compensation
Apply a business operation that offsets a prior effect when atomic rollback is unavailable.
Idempotency
Repeating the same logical request with the same key must not create an extra logical effect.
Long-running workflows
Persist timers, approvals and state across process restarts instead of keeping a request open indefinitely.
Human approval
Bind the approval to the exact action, scope, destination and policy revision that will execute.
Dead-letter queues
Isolate repeatedly failed events with their error context for review and controlled replay.

Automation tools:

Python
Implement workflow logic and tests with explicit state, dependency and effect boundaries.
N8n
Use visual workflow automation while testing retries, credential scope and durable state behavior.
Optionally Temporal / Restate / Dapr concepts
Compare durable execution tools against the same recovery contract before choosing a platform.

Work through an example

A worker validates an event, stores job=validated, then crashes before acknowledgement. The queue redelivers it. A unique event ID maps the duplicate to the existing job; the worker resumes from validated rather than creating a second job.

Cheat sheet

Events, checkpoints, and durable execution

Definition

A durable workflow records progress so interrupted work can resume after a failure.

Intuition

Recovery must reconcile external effects, not only restart computation.

Formula

effect_key=hash⁡(workflow_id,logical_action_id)\mathrm{effect\_key}=\operatorname{hash}(\mathrm{workflow\_id},\mathrm{logical\_action\_id})

Derive identity from the logical action, not from a retry attempt. Store the action result and reconcile unknown outcomes.

Common mistake

Retrying a timed-out write can duplicate an effect that already happened.

Production notes

Use checkpoints, stable idempotency keys, bounded retries and compensation.
