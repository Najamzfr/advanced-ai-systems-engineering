A useful plan is a typed graph, not free-form prose. Each task has an ID, objective, inputs, dependencies, allowed tools, evidence requirements, and acceptance criteria. Validate references and detect cycles before scheduling. Execute independent tasks concurrently only when their inputs and side effects permit it. Hierarchical planning decomposes a goal into subplans; graph planning makes shared dependencies explicit.

Replanning responds to new evidence or failed assumptions. Preserve the old plan and reason for change, bound the number of revisions, and carry remaining budgets forward. Never reset the budget merely because a new plan was produced. A verifier checks task outputs against acceptance criteria before a dependent task consumes them.

Planner–executor system

Planning

Task decomposition
Divide a goal into smaller tasks with verifiable outputs and explicit dependencies.
Plan-and-execute
Construct an initial plan, execute its tasks and revise it when observed evidence requires a change.
Replanning
Change unfinished work after new evidence or failure while retaining completed facts and budget usage.
Hierarchical planning
Break a high-level goal into subplans whose completion conditions remain connected to the original task.
Graph execution
Schedule tasks when their prerequisites are satisfied and propagate failure to dependent work.
State machines
Use guarded transitions to prevent invalid combinations of task status and external effects.
DAG orchestration
Coordinate acyclic task dependencies, retries and partial failures using recorded task state.
Reflection
Critique a previous result, then verify any proposed repair against evidence or tests.
Verification
Check a result against sources, executable tests or invariants before accepting it.

Work through an example

A comparison report needs facts about A and B before synthesis. A_source and B_source can run concurrently; compare depends on both. If B is unavailable, revise the output scope or return an evidence gap. Marking B complete with guessed facts is not a plan repair.

Cheat sheet

Plans as dependency graphs

Definition

A planner defines bounded work; executors perform steps and return evidence for review.

Intuition

Dependencies and acceptance conditions make a plan executable.

Pattern

Add a plan schema, topological validation, per-task acceptance criteria, and bounded replan history.

Common mistake

Parallel execution is invalid when a step depends on unfinished evidence.

Production notes

Persist plan revisions, step state, evidence references and retry limits.
