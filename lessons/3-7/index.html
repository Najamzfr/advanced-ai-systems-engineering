Expose a small service boundary: accept a typed research request, create a run ID, and return a report or explicit incomplete status. Health checks distinguish a running process from a ready dependency. Pass run/trace identifiers through retrieval and MCP calls. Record component duration, outcome, model/tool revision, and redacted error metadata.

Package a deterministic fixture mode and a real model mode separately. Pin dependencies, provide configuration validation, keep secrets out of the repository, and document one startup command. The Week 4 project needs this minimal runnable service and failure evidence now. Week 7 deepens it with queues, durable approvals, distributed telemetry, and release controls; those later topics should not be hidden prerequisites for the first project.

Work through an example

A research request fails because MCP is unavailable. The API returns incomplete with an error class and run ID; the trace shows retrieval succeeded but fetch failed. Returning an empty "successful" report would conceal the actual boundary failure.

Cheat sheet

A runnable and observable research service

Definition

Production architecture defines data, execution, policy and recovery boundaries.

Intuition

A deployed model is one component of a service with operational constraints.

Pattern

Run the service from a clean checkout; preserve a successful trace and a failed-dependency trace for Project 1.

Common mistake

A successful demo does not establish capacity or recovery behavior.

Production notes

Keep release gates, SLOs, canaries, rollback and incident evidence.
