ASSIGNMENT 01 / WEEK 01

Model Selection RFC

Select a model strategy using measured quality, latency, reliability, privacy, and monthly cost.

Realistic scenario

A customer-facing knowledge agent must handle 500,000 queries each month. Procurement needs a defensible primary, fallback, and routing strategy.

Objective

Select a model strategy using measured quality, latency, reliability, privacy, and monthly cost.

Constraints

  • Compare at least three strategies; benchmark at least two models as required by Lab 1.
  • Keep the RFC at or below 1,500 words. State token prices or local hardware assumptions with dates; do not invent live pricing.
  • Include burst load, sensitive inputs, provider failures, and retries in the design.

Required work

  • Define task slices, success criteria, and a representative query/output-length distribution.
  • Benchmark quality, p50/p95 latency, structured-output validity, and tokens per request.
  • Estimate monthly cost as request count × expected per-request usage, including routing, retries, and tool costs.
  • Specify routing thresholds, fallback behavior, privacy controls, and rollback criteria.
Original curriculum brief

Model Selection RFC

Scenario:

A customer-facing knowledge agent will process approximately:

500,000 queries / month

Design a model strategy.

Compare at least three options.

Discuss:

  • primary model
  • fallback
  • routing
  • latency
  • quality
  • monthly cost
  • privacy
  • failure behavior

Deliver:

  • RFC ≤ 1,500 words
  • benchmark
  • architecture diagram
  • decision table

Deliverables

  • RFC ≤1,500 words
  • Benchmark and raw results
  • Architecture diagram
  • Decision table comparing at least three options

Submission format: a reproducible repository with the memo/report, raw evidence, diagrams, configurations, and a README linking each required item. The site tracks your completion; it does not upload or grade submissions.

Grading rubric

CriterionWeightEvidence for full credit
Problem framing and constraints15%Explicit workload, success criteria, and relevant assumptions.
Experimental evidence30%Reproducible comparisons, raw results, proper splits, and uncertainty.
Architecture and trade-offs25%Alternatives considered and a decision supported by measurements.
Failure, security, and reliability20%Real failure cases, enforceable controls, and recovery behavior.
Clarity and reproducibility10%Traceable evidence, readable diagrams, and complete reproduction steps.

Rubric weights are course extensions. Unreproducible results or missing security/evaluation evidence do not satisfy the canonical hard pass requirements.

Technical-defense questions

  • What changes if the expensive model is only needed for 10% of queries?
  • Which slice would block release despite good average accuracy?
  • How will a silent provider revision be detected?
