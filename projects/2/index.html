GUIDED PROJECT 02 / WEEKS 05—08 · CORE

Customer Intelligence & Campaign Operations Platform

Build a reproducible system, measure alternatives, and defend the release.

Business problem

A customer-operations team needs reproducible segmentation and supported campaign drafts while controlling eligibility, approval, duplication, and review effort.

Business value

Reduce manual profile assembly and drafting time while maintaining factual and policy correctness. Measure review time, draft acceptance, grounding, and safe workflow completion.

Dataset

UCI Online Retail: 541,909 transaction records from December 2010 to December 2011, including InvoiceNo, StockCode, Description, Quantity, InvoiceDate, UnitPrice, CustomerID, and Country. The 22.6 MB workbook is licensed CC BY 4.0. Profile the downloaded file and preserve attribution.

CORE Dataset · 20 minOnline Retail. dataset and downloadReal transactions enable deterministic customer analytics and temporal evaluation.↗

Download the dataset archive ↗

The data has no campaign exposures, response labels, contact addresses, or consent records. Use explicitly synthetic contact/consent fixtures and a local simulated action sink. Do not infer or reconstruct real customer identities.

Learning objectives

  • Compute deterministic, temporally valid customer profiles.
  • Build evidence-constrained research and drafting agents.
  • Enforce eligibility and approval outside model prompts.
  • Operate durable, observable workflows and measure real task outcomes.

Architecture

Transactions → validation → cutoff-safe profiles → deterministic eligibility → scoped research/drafting → verification → exact approval → idempotent sandbox dispatch → outcome record.

System diagram

Technology choices

Python + FastAPI; pandas or SQL for deterministic profiles; PostgreSQL for transactions, jobs, approvals, and outbox; a typed MCP server; a bounded model client; a Python durable worker or local workflow engine; Docker Compose; OpenTelemetry collector and Grafana. Begin with SQL/product metadata; RAG remains optional and measured.

Prerequisites

Weeks 1–4 primitives, SQL or pandas, typed tool contracts, local containers, and explicit event/state modeling.

Milestones

Step-by-step build phases

PHASE 01

Ingest the real transaction dataset

Download UCI Online Retail and record its checksum/license. Read InvoiceNo, StockCode, Description, Quantity, InvoiceDate, UnitPrice, CustomerID, and Country. Profile missing IDs, cancellations, duplicate rows, nonpositive quantities/prices, and date coverage rather than trusting metadata alone.

Produce
raw manifest, schema, rejected-row report, and normalized transactions table.
Acceptance check
Reconcile row counts and gross/cancelled/net amounts; declare the treatment of each rejected/cancelled record.
PHASE 02

Compute cutoff-safe profiles

Choose a historical cutoff, for example 2011-10-01. Derive recency, distinct invoice frequency, and monetary value using only earlier valid purchases. Fix thresholds or fit segments on training data. Keep later transactions exclusively for offline outcome analysis.

Produce
customer_profiles(customer_id, cutoff, recency_days, frequency, monetary_value, segment, feature_version).
Acceptance check
No feature uses a future event; deterministic tests cover zero-history customers, cancellation, and currency/units.
PHASE 03

Create evidence and eligibility tools

Build a product catalog from known StockCode/Description records. Add explicitly synthetic campaign policy and consent fixtures, never pretend the dataset contains consent or email. Expose get_customer_profile, list_candidate_products, fetch_product_evidence, check_eligibility, and save_draft. Use SQL first; add RAG only if policy/document retrieval evaluation justifies it.

Produce
MCP server, policy.json, synthetic_consent.csv, and typed tool schemas.
Acceptance check
Profile access is scoped; unknown product attributes cannot appear as facts; opted-out fixtures are blocked deterministically.
PHASE 04

Research and draft under constraints

A research agent inspects purchase and product evidence. A proposal component suggests a segment-appropriate draft. A verifier checks facts, allowed fields, destination, and eligibility. Compare with a deterministic template and single-agent baseline before keeping specialists.

Produce
Draft(customer_id, evidence_refs, product_ids, text, policy_revision, model_revision, action_digest).
Acceptance check
Every factual statement has a source; no fabricated demographics, contact details, discounts, or conversion promises.
PHASE 05

Execute a durable approval workflow

Schedule profile refresh or accept a new-event fixture. Queue a job with stable event identity; checkpoint after validation and investigation. Store approval bound to the draft digest, destination, approver, and expiry. Send only to a local simulated campaign sink through an idempotent outbox. Track draft accepted/rejected, reviewer time, and dispatch status.

Produce
jobs, approvals, outbox, outcomes tables plus a sandbox action log.
Acceptance check
A changed draft requires new approval; duplicate events and worker restarts never duplicate the logical dispatch.
PHASE 06

Evaluate business and system behavior

Build 150 scenarios: normal eligible 30; useful segment/product candidates 30; misleading product text 15; contradictory policy 15; missing data 15; tool failures 15; prompt attacks 15; ambiguous consent/eligibility 15. Evaluate numeric correctness, grounding, policy compliance, reviewer acceptance/time, safe escalation, tokens, latency, and recovery.

Produce
Versioned cases, raw results, dashboards, security/fault tests, and final 10–15 page report.
Acceptance check
Report future-purchase ranking as an offline proxy only. No causal uplift claim without treatment/control evidence. Run clean deployment and rollback demos.

Deterministic profile example

valid = transactions[transactions.InvoiceDate < cutoff]
# Apply the documented cancellation and invalid-row policy first.
recency_days = (cutoff - last_purchase).days
frequency = count_distinct(valid.InvoiceNo)
monetary = sum(valid.Quantity * valid.UnitPrice)
# Later transactions are outcomes, never current features.

Evaluation methodology

Use the exact 150-scenario category allocation in Phase 6. Separate deterministic profile/eligibility correctness, model grounding, tool/argument accuracy, approval compliance, and end-to-end task success. Hold out later transactions for an offline ranking proxy; measure reviewer acceptance and task time with documented reviewer instructions. A controlled future pilot would be required for causal campaign uplift.

Metrics

  • Numeric/profile correctness and eligibility compliance
  • Grounding, unsupported product claims, tool/argument accuracy
  • Draft acceptance and measured reviewer task time
  • Duplicate dispatch count, recovery time, approval age, and safe escalation
  • p50/p95 latency, tokens, cost per completed approved task
  • Temporal future-purchase ranking as an offline proxy; no causal uplift claim

Failure scenarios

Inject missing customer ID, duplicate invoice, cancellation, stale feature cutoff, malicious product text, unknown product attribute, missing consent fixture, model/MCP/database failure, changed approved draft, duplicate event, and a worker crash after dispatch. Verify no unauthorized effect, no fabricated claim, and no duplicate logical send.

Security requirements

Scope profiles by allowed customer IDs. Never enrich identities or infer private traits. Validate tool arguments, rate-limit, restrict destinations, isolate untrusted text, and redact trace payloads. Approval must match the exact draft/destination digest and remain unexpired. All course campaign actions use the local sandbox sink.

Observability

Trace ingestion, profile calculation, eligibility, research, draft, verification, approval, and dispatch. Attach safe event/run IDs, feature/policy/model revisions, durations, tokens, errors, and retry counts. Link asynchronous spans and retain a redacted audit trail.

Workflow automation

Support scheduled profile refresh and event-triggered jobs. Persist checkpoints and pending approval; apply bounded retries and dead-letter handling. Use a transactional outbox and reconcile the sandbox sink by effect key.

Deployment

Provide a local Compose stack for API, worker, MCP server, database, and telemetry. Add health checks and a seed fixture command. Keep secrets outside Git. A deterministic fixture run must work without paid APIs; actual model experiments must be identified separately and disclose hardware or provider cost. Version the release and demonstrate clean setup, restart, and rollback.

make seed        # load declared fixtures
make test        # contracts and deterministic invariants
make eval        # versioned evaluation; record run mode
make up          # start local services

Grading rubric

Evaluation/evidence 25%; system/data correctness 20%; security 15%; reliability 15%; observability/performance 10%; reproducibility/report/defense 15%. No pass without automated evaluation, reproducibility, scoped tools, failure tests, and observability.
