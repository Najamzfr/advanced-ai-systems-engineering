GUIDED PROJECT 01 / WEEKS 01—04 · CORE

Evidence-First Deep Research Platform

Build a reproducible system, measure alternatives, and defend the release.

Build prerequisites in order

Each milestone starts from the previous artifact. Complete the linked teaching before implementing and defending the corresponding phase.

Required comparison contract. Retrieval has six configurations across four families: BM25-only, vector-only, hybrid without reranking, hybrid plus reranking, vectorless document-tree navigation, and long-context. Adaptation has six conditions: zero-shot, few-shot, advanced prompting, RAG, LoRA, and LoRA plus RAG. Freeze evaluation and budgets; larger sweeps are extensions, but these conditions remain required.

Business problem

A technical research team needs reports that identify supporting and contradictory evidence across documents, with traceable citations and an honest account of missing information.

Business value

Reduce evidence-finding and verification effort without replacing source judgment with fluent unsupported prose. Measure claim support and reviewer corrections.

Dataset

QASPER: 5,049 information-seeking questions over 1,585 NLP papers, with answers and supporting evidence. The dataset includes paper IDs, titles, abstracts, section text, questions, answers, and evidence annotations. Use a source-separated subset for feasible local runs; add multi-source and adversarial cases because the base task is primarily paper-grounded QA.

Learning objectives

  • Compare four retrieval families on identical evidence.
  • Build scoped tools and a bounded research runtime.
  • Separate verification from report generation.
  • Defend architecture with evaluation and failure evidence.

Architecture

Ingestion → normalized corpus → measured retrieval → scoped MCP → bounded research → evidence graph → independent verification → cited report.

System diagram

Technology choices

Python + FastAPI; SQLite/PostgreSQL for evidence and run state; BM25 plus a local vector index for the experimental baseline; document-tree JSON for navigation; a typed MCP server; a small model or existing model access; Docker Compose; OpenTelemetry. A vector database is optional until experiments justify it.

Prerequisites

Python, APIs, Git, Docker basics, basic retrieval, and the Week 1 evaluation harness.

Milestones

Step-by-step build phases

PHASE 01

Freeze the research contract

Create a 30-paper development corpus and a source-disjoint held-out sample. Build 80–100 questions across direct, multi-source, temporal, contradictory, ambiguous, absent-answer, and adversarial categories. Start with QASPER answer/evidence labels; label additions separately.

Produce
evals/cases.jsonl with question_id, paper_ids, question, evidence_ids, answer_type, category, and split.
Acceptance check
No source overlaps across splits; every case has an expected outcome or explicit unanswerability.
PHASE 02

Normalize and index

Parse QASPER full_text into source_id, section_id, paragraph_id, text, and provenance. Add a small public webpage/PDF/repository fixture set for adapter coverage. Build a content hash and extraction revision; reject parse failures with reasons.

Produce
sources.jsonl and a versioned manifest; fixtures for all four source types.
Acceptance check
Every returned passage can be traced to its original section/page and revision.
PHASE 03

Run the RAG Architecture Challenge

Implement BM25-only, vector-only, hybrid, hybrid plus reranking, vectorless document-tree navigation, and long-context baselines. Freeze generator and query budget. BM25-only is a required baseline. Include an oracle-context experiment only as a separately labeled diagnostic.

Produce
results/retrieval-ablation.csv and per-query run records.
Acceptance check
Compare recall, correctness, citations, context precision, latency, tokens, index size/build time, update complexity, and cost.
PHASE 04

Build typed research tools

Expose search_documents(query, scope), fetch_section(source_id, section_id), get_source_metadata(source_id), and store_evidence(claim_id, evidence_refs). Validate schemas and access scopes. Implement bounded planning with explicit evidence requirements.

Produce
mcp/server.py, tool contracts, runtime state, and test fixtures.
Acceptance check
Malformed arguments/results and unauthorized source access fail safely; repeated writes reuse effect keys.
PHASE 05

Separate verification from writing

Create Claim records with supports/contradicts edges. The verifier returns SUPPORTED, PARTIAL, CONTRADICTED, or INSUFFICIENT; the writer receives structured verdicts and cites material claims. Compare one agent to planner/researcher/verifier under equal budgets.

Produce
claim graph, cited report, and architecture experiment.
Acceptance check
No invented references; conflicts and gaps remain visible. Report unsupported-claim rate and citation completeness.
PHASE 06

Instrument, break, and release

Trace ingestion, retrieval, planning, tools, verification, and writing. Inject missing source, malicious text, failed MCP, timeout, and exhausted budget. Package the system locally and run it from a clean checkout.

Produce
Compose deployment, evaluation report, threat model, failure matrix, and five-minute demo.
Acceptance check
One documented command runs the fixture research flow; failures stop or degrade with honest evidence status.

  1. Use a fixed QASPER subset plus explicitly labeled multi-source/adversarial additions; split by paper before tuning.
  2. Normalize IDs, section names, paragraphs, revisions, and evidence offsets. Preserve whole-document text.
  3. Implement a common retrieve(query, scope, budget) contract returning evidence IDs, text, scores, cost, and timing.
  4. Build the four-family variants plus required BM25-only and hybrid-without-reranking baselines: six configurations total. Use one generator and answer schema.
  5. Run paired held-out evaluations and oracle-context checks. Audit missing evidence and unsupported answers separately.
  6. Measure index/storage/update complexity and warm/cold behavior. Choose the deployment for this workload using hard constraints and trade-offs.

PageIndex is a comparable navigation implementation. RAPTOR and GraphRAG are optional contrasts; neither name guarantees an embedding-free or chunk-free system.

Evaluation methodology

Retain the 80–100 question contract. Freeze splits and use the same generator across retrieval variants. Score evidence recall, answer correctness, citation precision/completeness, unsupported claims, tool selection, planner success, latency, and tokens. Calibrate any judge against human labels and preserve raw per-case evidence.

Metrics

  • Recall@K and oracle-context diagnostic
  • Factual correctness, citation precision/completeness, unsupported-claim rate
  • Tool/argument accuracy and planner success
  • p50/p95 latency, tokens, cost/request, index build/update time and bytes
  • Equal-budget architecture comparison and reviewer correction rate

Failure scenarios

Inject missing PDFs, extraction corruption, unreachable sources, contradictory dates, exhausted tokens, invalid tool responses, unsupported claims, and a failed verifier. Preserve partial evidence and do not label incomplete work as verified. Re-run the same question after recovery and explain state handling.

Security requirements

Separate trusted instructions from source content. Scope tool capabilities, restrict network destinations, prevent path traversal and SSRF, redact secrets, and require approval for any external publication. Include poisoned documents, malicious tool results, and unsupported citations in security tests.

Observability

Create one trace per research question with spans for planning, retrieval, reranking, each MCP call, verification, and report assembly. Record model/prompt/corpus revisions, token usage, latency, retries, evidence IDs, and support labels. Do not log credentials or private source text by default.

Workflow automation

Accept a research job, persist state, run bounded stages, checkpoint evidence, and return a cited report or explicit incomplete status. Retries reuse source and effect identity.

Deployment

Provide a local Compose stack for API, worker, MCP server, database, and telemetry. Add health checks and a seed fixture command. Keep secrets outside Git. A deterministic fixture run must work without paid APIs; actual model experiments must be identified separately and disclose hardware or provider cost. Version the release and demonstrate clean setup, restart, and rollback.
