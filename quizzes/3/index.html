WEEK 03 / INDEPENDENT ASSESSMENT

Defend your systems judgment.

Eight unseen scenarios. Draft your answers before revealing review criteria. These open-ended answers require self, peer, or instructor review.

Diagnostic quiz

Complete four automatically checked diagnostics, then write your answers to the eight independent scenarios below. The written defenses use a separate review rubric.

Identify the bug

store_result succeeds on the server, but the response times out. What is the safe next step?

Multi-select

A read-only client discovers search and delete tools. Which controls still apply?

Sequencing

Order one bounded agent iteration.

Matching

Match field to its purpose.

This page saves drafts and rubric ratings; it does not automatically grade technical reasoning. Score each response 0 (missing/incorrect), 1 (partial), 2 (sound with a gap), or 3 (sound and justified). A suggested readiness threshold is 18/24, with no unresolved authorization or evidence-integrity errors. Ratings are self-reported unless you record an external reviewer.
SCENARIO 01 / 08

An invoice service needs parse, calculate tax, validate, and save in a known order. A proposal adds an autonomous supervisor. Defend your architecture choice.

Reveal the review criteria

Prefer explicit workflow for known transitions; deterministic tax and validation; an agent requires evidence of variable decision needs and measured gain, not number of LLM calls.

SCENARIO 02 / 08

The model asks for a fourth tool call after the global call limit of three. It says the call is essential. Specify runtime behavior.

Reveal the review criteria

Runtime budget wins; no call executes; persist incomplete/escalation status and remaining evidence need; do not let a model reset limits.

Review unit 3-2: Build a bounded ReAct loop →

SCENARIO 03 / 08

A tool returns success=true with a negative quantity for an operation requiring positive units. Which boundary failed and how should the host respond?

Reveal the review criteria

Result-domain validation failed despite schema/transport success; reject/quarantine, retain redacted error evidence, avoid downstream effect, test server and host contracts.

Review unit 3-3: Tool contracts, effects, and unknown outcomes →

SCENARIO 04 / 08

Two network attempts use different trace span IDs but the same operation key. Is that correct? Describe how to store them.

Reveal the review criteria

Yes: attempt identity differs from logical effect identity; associate both attempts with one persisted operation/sink result and reconcile unknown outcomes.

Review unit 3-3: Tool contracts, effects, and unknown outcomes →

SCENARIO 05 / 08

Draw the responsibilities when one host connects to a documents server and a calculations server. Where do credentials and authorization belong?

Reveal the review criteria

Separate clients/connections; host owns interaction/policy/context; servers validate access; credentials stay out of model context; discovery is not authorization.

Review unit 3-4: MCP host, client, and server boundaries →

SCENARIO 06 / 08

A local MCP file tool accepts a symlink inside the allowed root that resolves outside it. Explain why the roots list did not protect the file.

Reveal the review criteria

Roots advertise intended scope, not OS enforcement; resolve/canonicalize safely, check real-path containment and filesystem permissions, reject traversal/symlink escape.

Review unit 3-5: Implement and test an MCP connection →

SCENARIO 07 / 08

The framework port succeeds on fixtures but uses hidden automatic retries. Design an equivalence test against the scratch loop.

Reveal the review criteria

Record actual provider/tool calls, budgets, retries, side effects, stop states and schema errors on identical fixtures; disable/control defaults or justify bounded differences.

Review unit 3-6: State, memory, and framework equivalence →

SCENARIO 08 / 08

A process is healthy but its MCP dependency is unavailable. Define readiness, task outcome, and trace evidence for a research request.

Reveal the review criteria

Separate liveness from readiness; return typed incomplete/failure or bounded queue status; preserve run ID and failed-stage span; HTTP success alone is not task success.
