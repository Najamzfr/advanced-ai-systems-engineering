LAB 4 / WEEK 04

Is Multi-Agent Actually Better?

Determine whether coordination earns its complexity on the same research task.

Objective

Determine whether coordination earns its complexity on the same research task.

Prerequisites and starting inputs

Labs 1–3; evidence corpus; Project 1 evaluation questions.

Finish the final learning unit for Week 4, then run the starter fixtures. Preserve the preceding week's artifact and configuration.

Architecture

Warm-up diagnostic

A research task needs citations, one optional follow-up search, and a report. A team proposes twelve autonomous specialists.

Select the essential components for a defensible first release.

Diagnostic hint

Keep the components needed for evidence and control before adding specialists.

Diagnostic reasoning

Start with one bounded runtime, scoped tools, claim verification, and evaluations. Add coordination only after equal-budget experiments justify it.

This browser check validates the stated fixture rule, not completion of the implementation lab.

Guided implementation path

Starting artifact: the final unit of Week 4 and the preceding week's versioned experiment/state contracts. Download and run the engineering fixtures →

Use Python 3.10+ for the standard-library fixtures. Live model, framework, MCP and GPU experiments require separately pinned dependencies and declared hardware/provider access. Keep deterministic fixture results separate from real measurements.

CHECKPOINT 1 / 5 · WORKED START

Establish the input contract

Define Task(id, dependencies, evidence_need, allowed_tools, acceptance) and validate missing references/cycles.

Expected intermediate result
A valid plan has an executable order; a cyclic fixture is rejected before tools run.
Stuck? Inspect this boundary

Two tasks waiting on each other is a planning error, not a reason to extend timeouts.

CHECKPOINT 2 / 5 · GUIDED BUILD

Implement and inspect

Implement single-agent, planner–executor and planner–researcher–verifier variants using the same tools.

Expected intermediate result
All variants produce the same claim/evidence/verdict schema.
Stuck? Inspect this boundary

Keep writer and verifier boundaries explicit; summaries do not substitute for sources.

CHECKPOINT 3 / 5 · GUIDED BUILD

Implement and inspect

Inject worker timeout, duplicate task, contradictory evidence, malformed output and exhausted budget.

Expected intermediate result
Partial evidence and failed workers remain visible; replanning does not reset budgets.
Stuck? Inspect this boundary

Merge by evidence identity and preserve contradictions rather than voting away disagreement.

CHECKPOINT 4 / 5 · INDEPENDENT TRANSFER

Implement and inspect

Run the same held-out cases and total call/token/time budgets for all three architectures.

Expected intermediate result
Paired quality, unsupported-claim, cost and tail-latency comparison.
Stuck? Inspect this boundary

A nominal step count can hide subagent calls; inspect actual provider usage.

CHECKPOINT 5 / 5 · INDEPENDENT TRANSFER

Produce the evidence

Choose the least complex passing architecture and integrate the Project 1 release.

Expected intermediate result
80–100 question evaluation, reproducible deployment, trace evidence and defense.
Stuck? Inspect this boundary

Use the assignment as the project review; do not duplicate the report.

Required experiments

Implement the same task three times:

Version A

Single agent

Version B

Planner → executor

Version C

Supervisor + specialist agents

Measure:

  • success rate
  • latency
  • number of model calls
  • token usage
  • errors
  • reproducibility
  • debugging complexity

Students must justify which architecture should be deployed.

Compare all three architectures at equal budgets. Ablate verification and shared memory separately; include contradictory evidence and one failed worker.

Metrics and interpretation

Success rate; latency; model calls; tokens; errors; reproducibility; debugging complexity.

Preserve per-case outcomes, denominators, model/data/configuration revisions, run mode, paired comparisons and uncertainty. Separate deterministic fixtures from live measurements.

Failure cases

Cascading errors; duplicated work; conflicting claims; deadlock; missing worker result; unbounded delegation.

Deliverables

Three runnable variants, paired result table, failure traces, and a justified deployment decision.

Include every guided checkpoint, raw experiment results, failed cases, a decision memo and reproduction instructions.

Stretch goals

Plot a quality–cost frontier across task difficulty and identify a routing policy.

Extra scale, frameworks and sweeps follow the required experiment; they do not replace it.
